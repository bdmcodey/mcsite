Automating MARC Holdings Generation with AI: Lessons from the Field

Built with an AI coding assistant; runs without one.

Matthew Codey

Part 1

The problem, and the approaches I tried

The problem

Many libraries' serials holdings are stored only as human-readable, free-text 866 fields rather than as MARC-encoded 853/863 pairs. Converting by hand is slow, different conventions for textual holdings may have been followed, and hand-typed data is prone to typos and other errors.

The goal: a tool that is portable across different collections of records, works on messy holdings as they are (no manual clean-up), and never silently loses anything.

Three ways to get from an 866 to an 853/863, each asking something different of the person doing it.

Approach 1

Write the script by hand

Write the parsing code yourself: a regular expression and a script, built against your own collection's 866s.

My starting point was a script USC colleagues wrote for ONE Archives serials migrated from Inmagic, which read 866s written year first (Chung & Pendyala, 2023). I adapted it, but it was written for that one collection and expected a single 866 per record, so it did not translate well to my library's records.

Coding knowledge
The most.
For it
Results tuned to a bespoke collection. This is how the original parser's regular expression was written.
Against it
Hard to make portable: a pattern written for one collection's habits does not carry to another's, and generalising it by hand reached the limit of what I could do. It is only feasible when the 866s are already fairly clean and follow a consistent pattern; the messier they are, the harder it gets. That runs against the aim, which is a tool that works on messy holdings as they are, without a manual clean-up first, and without losing confidence that nothing is being silently lost.

To write: the experience in more detail.

Approach 2

Ask a model to convert

Send the 866 statements to a large language model through its API and have it write the 853/863 directly: no parser, no regex.

Coding knowledge
The least.
For it
In limited testing, good results with little setup.
Against it
Expensive in tokens: rate limits arrived almost at once. And a model's output is stochastic, so the same corpus sent to the same model twice is likely to come back converted differently.

To write: the experience in more detail.

Approach 3 · chosen

Use AI to build the tool

Describe in plain language what the tool should do and how its screens should work, and have an AI coding assistant (Claude Code) write a deterministic Python application from that. It produced the Pattern Detector and the Converter first, then the Workbench that combined them.

Part 2

The approach chosen: AI-assisted development of a deterministic tool

Built with an AI coding assistant; runs without one

The result is the MARC Holdings Workbench, a Python application. It uses no AI when it runs: no model, no network calls, no API key, and nothing leaves the machine. The same file converts the same way every time. The AI was in how it was built: a library paraprofessional, not a developer, working with an AI coding assistant, release by release.

How the Workbench reads a statement

Two parts read every file. The pattern detector sorts all of a file's 866 statements into groups of the same shape, so that a cataloguer decides what something means once per group rather than once per record. The standard parser reads each statement into volumes, issues and dates, and stops rather than guesses. Here is the statement from the top of the page, as the detector reads it.

Each piece is recognised by a fixed list of rules, tried in order, and the first rule that fits wins. The order is what makes it read the way a cataloguer would: 1992 is a year before it is a number, Nov. is November before it is "no" followed by "v.", and a caption counts only where a word starts. Spaces are set aside, so v.1 and v. 1 have the same shape. The long dash marks the hyphen that divides the start of the holdings from the end; the hyphen inside the dates means "through".

3 · A matching rule, with a slot for each value

Statements with the same labels in the same order are one group, whatever their numbers. For each group the detector writes a regular expression: the captions it saw, and a named slot for each value. 4 · Confirm once, for the whole group

Each group appears as a card: its shape, how many statements it holds, and a row for each slot with the detector's guess filled in. For each value the cataloguer can set what it is (enumeration, year, month or season, day, or not encoded), its caption, its level, and whether it opens or closes the range. What confirming changes depends on the group:

  • Nothing to decide. In this group every value carries its own caption, so the parser reads these statements in full and the pattern is confirmed without asking.
  • A caption to supply. In {{ pat.uncaptioned.statement }}, from the same sample, the {{ pat.uncaptioned.suggested_value }} has no caption; its shape is {{ pat.uncaptioned.shape }}. The card suggests v. but still asks. On its own the parser writes $a (*), the standard's placeholder for an unnamed level; with v. confirmed, the 853 reads $a v. $b no.
  • A reading only the cataloguer can give. A lone number with no caption and no date could be a volume, an issue or a year. The parser holds it rather than guess, and the meaning confirmed on its pattern is what converts it.

5 · The parser reads; the pattern fills the gaps

A confirmed pattern decides which statements are its own, and supplies only what the parser cannot know: the meaning of a bare number, or a caption for a level written without one. It never overwrites a caption the statement prints. Wherever a statement says everything itself, the pattern and the parser alone write the same 853 and 863, and a test checks that both routes agree.

What the cataloguer controls

The cataloguer decides what "correct" means, and the Workbench is built to take those decisions: for a group of statements, for one record, or for the whole file.

On a pattern

  • Confirm or change what each value is, its caption and its level.
  • Mark a shape Skip to handle it by hand; its statements are left exactly as they are.
  • Test the expression against statements, or edit it by hand.
  • Export the pattern library and load it next week, or on another collection.

On one record

  • Edit an 866 before conversion, to fix a typo such as (Fal 1995-Fall 1999) or a wrong caption. The corrected text goes into the file, and "Put back as uploaded" undoes it.
  • This record's 853: its frequency ($w), issues per volume ($u), and a caption for any level its statements leave blank.
  • Skip the record, give each shape its own 853, mark it reviewed, or leave a note for the log.

For the whole file

  • Holdings level: detailed (4) or summary (3).
  • Subfield convention: MARC 21, or a house convention adjustable subfield by subfield; the 853 indicators and numbering continuity ($v).
  • Whether the parser converts statements no pattern claims, and strict mode: convert only what it reads in full.
  • What to do when a value would be left out to fit MARC: convert and mark it, hold that statement, or leave the record as uploaded.
  • Whether to remove each 866 (only ever once everything in it went somewhere), and whether to clear existing 853/863s first.

Every record says what happened to each statement: converted, to check, left out to fit MARC, held, or belongs in an 867 or 868. A "Needs attention" filter gathers what is left to do, and the downloadable log lists every decision ("Edited by you", "853 set by you", "Skipped") beside what the tool did.

The working rules

Written down in the project's contributing guide "because most of them were arrived at by getting something wrong first":

  1. Measure before you change. Count what actually happens on the corpus before writing a fix.
  2. Nothing disappears silently. Every value is encoded, dropped with a warning that names it, or held for review with nothing written.
  3. One reader of holdings. One parser reads every statement; a confirmed pattern supplies only what it cannot settle.
  4. If a fix needs the tests rewritten, stop. It is usually arguing with the design rather than fixing a bug.
  5. Write the changelog for cataloguers. Say what changed about the output or the screen, not how the code changed.

The turning point: silent losses

A refusal is safe: nothing is written and the 866 stays. A silent loss is not: fields are written, the 866 is removed, and a volume or a month is gone with nothing on screen to say so. Two tools became one

The Pattern Detector and the Converter came first. On 25 August the Workbench arrived to combine them: find the patterns, confirm what they mean, convert in one place. For three weeks all three ran side by side, duplicating each other's code, until the copies drifted far enough that one deleted the other's pattern libraries. On 16 September the Workbench absorbed both, and they were retired.

The human in the loop

The AI writes the code; the cataloguer decides what "correct" means. Two bugs from October were found by the cataloguer, not by the tests:

  • In v. 58 Suppl. (Sep 2003), confirming the pattern it arrived with wrote the volume and date and dropped "Suppl." without a word. Found in a demo dry run; fixed in 0.32.0.
  • 34 no 3, 4 (Summer, Autumn 1990), a list of runs, ignored the caption confirmed for it. Found in testing; fixed in 0.34.0.

Lessons, and what's next

Draft: edit freely

A script reads what it was written for, and passes over the rest. In the clean-up this work grew from, about 600 of 5,254 records came out with no 863, and were found afterwards by looking for what was missing (Chung & Pendyala, 2023). That is the ordinary risk of matching patterns, not a fault of that script, and it matters most when the original 866 is removed so the ILS can rebuild it: a statement that was skipped or only partly read can take the only record of what is held with it. The Workbench makes the check part of the tool. Every value in a statement is encoded, or named as left out, or the statement is held for review and its 866 kept.
