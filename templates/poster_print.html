1 The problem, and the approaches I tried

The problem

Many libraries' serials holdings are stored only as human-readable, free-text 866 fields rather than as MARC-encoded 853/863 pairs. Converting by hand is slow, conventions vary, and hand-typed data is prone to typos and other errors.

The goal: a tool that is portable across collections, works on messy holdings as they are (no manual clean-up), and never silently loses anything.

{{ coloured(n.statement.segments_853) }}{{ coloured(n.statement.segments_863) }}

Approach 1

Write the script by hand

I adapted USC colleagues' script (Chung & Pendyala, 2023) over six months, teaching myself Python. The hardest part was one monolithic regular expression: weeks, if not months, in regex101 before it covered every pattern.

Pros: tuned to one collection; code I knew line by line.

Cons: only feasible on clean, consistent 866s, and not portable. Few institutions could write their own expression that way.

Approach 2

Ask a model to read the statements

Send the 866s to a large language model through its API, and ask it to pick out the volumes, issues and dates an 853/863 is built from.

Pros: the least coding knowledge; good results from minimal prompting.

Cons: tokens for every statement (free access stopped within two dozen records), and output that isn't guaranteed to be the same twice.

Approach 3 · chosen

Use AI to build the tool

Describe in plain language what the tool should do, and have an AI coding assistant (Claude Code) write a deterministic Python application.

Pros: the same file converts the same way every time, with no model, API key or tokens when it runs.

Cons: a black box. I can confirm it works, and tests stop it regressing, without fully understanding why it works.

2 The approach chosen: AI-assisted development of a deterministic tool

How the Workbench reads a statement

{{ coloured(pat.template_segments) }}

  1. Statements with the same shape are one group, whatever their numbers.
  2. Each group gets a matching rule with a named slot for each value.
  3. A cataloguer confirms what each value means, once per group.
  4. The parser reads every statement; a pattern fills only what it cannot know.

What the cataloguer controls

  • On a pattern: what each value is, its caption and level; skip a shape; test or edit the rule; reuse the library on another collection.
  • On one record: edit an 866 before it is read, set this record's 853 (frequency, issues per volume, missing captions), skip it, leave a note.
  • For the whole file: holdings level, subfield convention, strict reading, what to do with a value MARC has no place for, and whether to keep each 866.

Every decision is listed in a downloadable log.

The working rules

  1. Measure before you change.
  2. Nothing disappears silently.
  3. One reader of holdings.
  4. If a fix needs the tests rewritten, stop.
  5. Write the changelog for cataloguers.

The human in the loop

The AI writes the code; the cataloguer decides what "correct" means. Two October bugs were found by the cataloguer, not the tests:

  • v. 58 Suppl. (Sep 2003) lost "Suppl." when its pattern was confirmed (fixed in 0.32.0).
  • 34 no 3, 4 (Summer, Autumn 1990) ignored its confirmed caption (fixed in 0.34.0).

The turning point: silent losses

A silent loss writes the fields, removes the 866, and drops a volume or a month with nothing on screen to say so.

Lessons, and what's next

  • A script reads what it was written for, and passes over the rest. The Workbench makes the check part of the tool: every value is encoded, named as left out, or held with its 866 kept.
  • Decide whether you can work with code you don't fully understand. A test suite and automated checks are what made it acceptable.
  • AI is at its best building the tool, not being it.
  • Next: testing on more real .mrc files from technical services colleagues, working toward a 1.0 release.
